## 一、顶层逻辑

v20.2 继续沿着 v20 商业化产品套餐方向推进，但产品表达必须从“云平台能力”转成“小白用户能理解的服务”。

本次开发必须遵守下面三条结构原则：

- 模块间低耦合：Portal 界面、计费策略、T+1 精准账单归因、OPL 网关、资源开通/删除、云资源库存只通过明确 API 和结构化数据交互，不能靠共享临时状态串联。
- 模块内高聚合：每个模块只负责自己的职责。余额和冻结策略归计费域；云资源删除归资源开通模块；用户看见的文案归 Portal 展示层；T+1 账单解析归账单归因模块。
- 模块互不影响：修 OPL 回复不能改 `.runtime/one-person-lab-upstream`；账单页面改版不能影响资源删除；Sentrux 结构瘦身不能改变已有公开路由和 API 合约。

## 二、开发目的

v20.2 的目标是让平台可以更接近“面向小白用户的商业化运营”，而不是只给技术人员看。

普通用户不需要理解 Kubernetes、COS、CVM、TKE、节点池、账单归因等术语，也应该能回答四个问题：

- 我买了什么？
- 我买的东西可以做什么？
- 我用了多久？
- 我花了多少钱，为什么扣这些钱？

管理员需要能快速回答四个运营问题：

- 现在是谁在花钱？
- 哪个客户余额不足或扣费异常？
- 哪些云资源属于哪个客户、订单、任务？
- 哪些 T+1 精准账单已经结算、还在预扣、或等待归因？

## 三、小白商业化硬内容

v20.2 的商业化边界是“受控商业化运营”，不是完全自助商业化。原因是本版本不包含外部支付网关、发票、税务和多币种结算；充值仍以后台充值或受控运营为主。

面向小白用户，v20.2 必须补齐下面硬内容：

- 套餐售卖页：展示套餐名、适合谁、包含什么、能跑什么、有什么限制、超出怎么算。
- 购买和充值闭环：用户能看到当前套餐、余额、冻结金额、充值记录、消费记录；管理员能给用户充值并核对 ledger。
- 新手路径：注册/登录后能按“选套餐 -> 建工作空间 -> 上传文件 -> 启动任务 -> 查看回复/结果 -> 下载文件 -> 查看账单 -> 删除服务器”的顺序完成一次任务。
- 失败解释：余额不足、API key 无效、任务失败、文件过大、服务器释放失败、T+1 账单未归因时，都必须给出用户能理解的说明。
- 服务边界：说明文件保留多久、删除服务器后是否还能下载已生成结果、预扣和 T+1 校准是什么意思。
- 安全边界：API key 不落日志，COS signed URL 和临时 token 不入库、不入文档、不入 evidence；普通用户不能看到其它用户文件、账单、资源编号。
- 客服/人工处理入口：账单归因失败、资源释放失败、充值异常时，用户看到“联系管理员/等待处理”的明确状态，管理员看到处理原因和技术证据。
- 运营指标：管理员能看到客户数、今日消费、本月消费、累计消费、充值总额、未结算金额、未归因账单、运行中资源、释放失败资源。

这些硬内容对应的详细 API、页面、状态机、文件范围和测试命令，见配套实施计划。

## 四、产品语义

### 1. 冻结一周与余额不足提醒

冻结资金是服务保障机制，不是立即停机机制。

- 用户购买套餐后，平台冻结一周服务保障金。
- 日常套餐费和运行中资源费用可以按计费策略消耗、预扣或与冻结金额做校准。
- 如果普通可用余额不足，但冻结资金仍能覆盖当前承诺的一周服务，用户应看到提醒，而不是马上被停机。
- 如果“可用余额 + 可使用冻结覆盖”已经不足以覆盖下一周期或新的付费动作，平台应阻止新付费工作，并明确告诉用户需要充值多少。
- 宽限期内，已经生成的可下载结果应继续允许下载，除非文件保留期已经到期。

面向用户的表达要口语化，例如：

- “你已购买入门套餐。它包含 10GB 存储，适合小型任务和文件分析。”
- “本周已预留 28 元服务保障金。当前余额偏低，但本周服务还能继续。建议充值，避免下周无法继续运行。”
- “这次任务使用了服务器 18 分钟，当前先按运行中费用预扣，最终金额会在腾讯云 T+1 账单回来后校准。”

### 2. 存储表达

普通用户不应看到“开通 COS”或“对象存储开通”这类云操作。

v20.2 应把存储表达为套餐能力：

- 套餐存储容量
- 已用容量
- 上传文件
- 下载结果
- 扩容

后端仍保留 `storageOrders`、存储权益、COS key、workspace 文件记录，用于审计、计费和归因；这些技术数据不删除，但不直接暴露给普通用户。

### 3. 资源编号与删除安全

每个付费计算资源必须保留确定性的身份链路：

- 用户/租户 id
- workspace id
- 资源订单 id
- run id
- server plan id
- node pool id
- CVM instance id

Portal 普通用户侧展示成“服务器编号”和“任务编号”；管理员侧可以展示完整技术 id。

删除服务器时必须按强绑定链路删除，不能只靠模糊名称或列表顺序判断，避免删错客户资源。

## 五、前面 11 点问题的纳入情况

你前面提到的问题已经纳入 v20.2 方案。原消息里编号有跳号和重复，我按实际问题拆成 11 项核对：

1. COS 临时签名账单地址：已纳入 P0 “T+1 精准账单从 COS 回放”。方案明确不能把 signed URL、token 或临时凭证写进源码/文档，只能用 object key 或密钥方式读取。
2. 存储和账单关系：已纳入“存储表达”和“客户可读账单”。普通用户看套餐容量、已用容量、文件和扣费；管理员看存储订单、文件记录和账单归因证据。
3. 任务空间里的“对象存储开通”是否还需要：已纳入 P1 “Portal 信息架构瘦身”。普通用户侧不再需要单独展示“对象存储开通”，改成套餐存储和扩容入口；后端记录保留。
4. 运行总台的关键入口是否多余：已纳入 P1。普通用户导航收敛到总览、套餐、工作空间、账单、轨迹；“关键入口”如果不能服务这些主流程，应删除或降级。
5. 告警概览是否多余：已纳入 P1 “公告与告警清理”。普通用户侧不保留泛泛的告警概览，只保留需要行动的提醒。
6. 公告与警告里的告警列表有什么用：已纳入 P1。告警列表只保留低余额、账单归因失败、资源释放失败、OPL key 缺失或无效、精准账单导入失败这类需要处理的事项。
7. 计费运维里的待处理记录是什么意思：已纳入 P0 “客户可读账单与冻结策略”。待处理记录要改成用户能理解的“运行中预扣”“等待 T+1 校准”“待补扣/待退款/待归因”。
8. 成本构成不清楚：已纳入 P0。账单要解释套餐费、服务器运行费、存储费、预扣金额、最终校准金额，而不是只展示内部成本结构。
9. 管理员应该能看到每个人花了多少钱、今天花了多少、总共花了多少、充值记录：已纳入 P0 管理员客户账务视图，是 v20.2 必须交付的核心项。
10. “K8s 运维与分发”是否还有用：已纳入 P1。普通用户不展示；管理员侧改成“云资源状态”，从腾讯云/TKE/CVM/资源映射里摘取只读状态和清理证据。
11. `opl.medopl.cn` 发送消息没有回复：已纳入 P0 “OPL 消息不回复 bug”。必须通过浏览器级 live smoke 证明登录、绑定 `gflabtoken`、发送消息、收到非空回复。

## 六、P0：v20.2 必须交付

### 1. 修复 OPL 消息不回复

问题：

- `opl.medopl.cn` 能用 Portal 账号和 `gflabtoken` 登录，但浏览器里发送消息后没有回复。

开发方式：

- 用浏览器级证据诊断：登录、输入 API key、发送消息、观察网络请求、WebSocket/SSE、网关日志、upstream 响应、浏览器 console。
- 保持 `.runtime/one-person-lab-upstream` 干净，不修改原始 runtime 源码。
- 只允许修网关、启动桥接、provider key 传递、WebSocket 代理、Portal launch contract 等外层集成。
- 增加可重复 live/browser smoke，证明一个真实用户可以发送消息并收到非空回复。

交付边界：

- 范围内：OPL 登录、API key 绑定、消息发送、回复接收、网关代理、session launch、日志证据。
- 范围外：重做 OPL upstream UI、修改 upstream runtime 行为、新增新的 LLM provider。

测试方式：

- `node scripts/check-one-person-lab-upstream-clean.mjs`
- 现有 OPL gateway 合约测试。
- 新增 `opl.medopl.cn` 浏览器 live smoke：登录 -> 输入 API key -> 发送消息 -> 收到回复。
- 日志检查：不能打印 API key。

### 2. 客户可读账单与冻结策略

问题：

- 用户需要看懂自己买了什么、为什么扣费。
- 管理员需要看到每个客户花了多少钱，而不是只看内部归因记录。

开发方式：

- 把冻结、提醒、拦截规则收敛到独立计费策略模块。
- 用户侧展示：
  - 套餐名称
  - 包含存储
  - 当前余额
  - 本周冻结金额
  - 今日消费
  - 本月消费
  - 累计消费
  - 充值记录
  - 运行中预扣
  - T+1 精准结算状态
- 管理员侧增加客户账务视图：
  - 一行一个客户
  - 余额
  - 可用余额
  - 冻结金额
  - 今日消费
  - 本月消费
  - 累计消费
  - 累计充值
  - 运行中资源
  - 计费风险状态
- 客户详情页展示：
  - 充值记录
  - 扣费记录
  - 退款记录
  - 补扣记录
  - 当前资源订单
  - 历史任务
  - 相关文件和轨迹

交付边界：

- 范围内：wallet、ledger、pending、exact、recharge、refund、makeup、freeze 的展示和聚合。
- 范围外：外部支付网关、发票、税务、多币种结算。

测试方式：

- 冻结状态合约测试：
  - 余额充足。
  - 可用余额低，但冻结金额覆盖当前一周。
  - 冻结不足以覆盖下一次付费动作。
  - 宽限期允许下载结果。
  - 达到风险阈值后阻止新付费工作。
- 管理员 API 合约：每个用户的总消费必须能和 ledger 明细对齐。
- Portal frontend typecheck/build。
- live 用户链路：新建用户、充值、产生消费后，管理员客户账务能看到充值和消费。

### 3. T+1 精准账单从 COS 回放

问题：

- 你提供过的 COS signed URL 带临时凭证，不能提交或保存。
- `20260502` 账单对象可用于验证解析和归因流程，但不一定覆盖 2026-05-03 的 v20.1 live run。

开发方式：

- 使用 COS object key 或密钥访问，不把 signed URL 字符串写入源码或文档。
- 先对 `20260502` 对象做 exact bill preview，验证 ZIP 解析、列名标准化、资源 id 提取、未归因队列。
- 当 `20260503` 账单对象可用后，对 v20.1/v20.2 目标资源链做精准归因。
- 如果腾讯云账单没有资源标签，只允许通过 Resource Provisioner 保存的资源 id 映射做确定性归因。

交付边界：

- 范围内：COS ZIP 读取、账单行解析、preview、归因、精准扣费/退款/补扣、未归因队列。
- 范围外：用未覆盖目标资源运行窗口的账单对象声明“精准结算完成”。

测试方式：

- 本地 ZIP parser smoke。
- COS live preview，使用 object key 或密钥访问。
- reconcile 幂等测试：第二次运行不能重复扣费。
- 每条结算结果必须且只能进入一种分支：
  - 精准扣费
  - 退款
  - 补扣
  - 未归因并带原因

### 4. 删除服务器与停止计费可见化

问题：

- v20.1 已经强化删除绑定，v20.2 要让用户和管理员看得懂删除结果。

开发方式：

- 用户侧用口语化状态：
  - “服务器准备中”
  - “运行中”
  - “正在释放”
  - “已释放，停止计费”
  - “释放失败，请联系管理员”
- 管理员侧展示技术 id 和清理证据。
- 用户侧只展示服务器编号、任务编号、使用时长、是否停止计费。

交付边界：

- 范围内：Portal 展示和管理员证据。
- 范围外：除非发现 bug，否则不改变 v20.1 的强绑定删除语义。

测试方式：

- 现有 delete-binding 负向测试。
- live same-day E2E 清理后必须证明 Kubernetes 项为 `0`、node pool 为 `0`、CVM instance 为 `0`。

### 6. 公告与告警清理

问题：

- 当前“公告与告警”混合了平台通知、技术告警和不明确列表，普通用户看不懂。

开发方式：

- 公告只保留面向用户的平台消息。
- 告警只保留需要行动的事项：
  - 余额不足。
  - 账单归因失败。
  - 资源释放失败。
  - OPL provider key 缺失或无效。
  - 精准账单导入失败。
- 普通运营流程里移除泛泛的“告警概览”。

交付边界：

- 范围内：告警分类、管理员告警列表、用户提醒文案。
- 范围外：完整事故管理系统。

测试方式：

- 已知状态触发告警的合约测试。
- 低余额/冻结提醒文案 UI 测试。

### 7. “K8s 运维与分发”改成“云资源状态”

问题：

- “K8s 运维与分发”太技术化，不适合商业化运营页面。

开发方式：

- 管理员侧改名和重构为“云资源状态”。
- 状态来源：
  - Resource Provisioner 资源映射。
  - TKE node pool 库存。
  - CVM 库存。
  - 清理证据。
- 原始 K8s 细节只放在管理员高级详情里。

交付边界：

- 范围内：管理员状态页和 API payload。
- 范围外：把 Kubernetes 控制操作暴露给普通用户。

测试方式：

- active/deleted/failed 映射 fixture 的管理员资源状态合约。
- 只读 live inventory 检查。

### 8. 备份与恢复证据

开发方式：

- 写清 PostgreSQL/Redis 备份要求。

- `sentrux check .` 要记录结果，并尽量提升 v20.1 的 `quality_signal`、`modularity`、`equality`。

## 九、开发推进方式

v20.2 按互不干扰的切片推进：

1. OPL 回复诊断与网关修复。
2. 计费/冻结策略和客户账务 payload。
3. Portal UI 文案与导航瘦身。
4. T+1 COS 精准账单 preview/reconcile。
5. 云资源状态页。
6. Sentrux 结构瘦身。

每个切片都必须遵守：

- 先写或扩展合约测试。
- 只改拥有该职责的模块。
- 跑对应 focused tests。
- 跑 Portal 共享检查。
- 结构调整后重新跑 `sentrux gate .`。
- 更新 v20.2 更新日志，记录做了什么和哪些证据通过。

## 十、发布边界

v20.2 只有满足下面条件，才能称为“受控商业化运营版本”：

- OPL 浏览器消息回复能用真实 `gflabtoken` 跑通。
- 普通用户看到套餐、存储、账单语言，而不是云基础设施语言。
- 管理员能看到每个客户的余额、充值、今日消费、本月消费、累计消费、运行中资源、计费风险。
- 冻结策略能在硬拦截前提醒用户，并解释冻结资金是否还能覆盖当前服务周期。
- v20.2 部署后 same-day live E2E 通过。
- COS 精准账单 parser 和 preview 能用提供的账单对象跑通，且不提交 signed URL 凭证。
- 如果已有覆盖 v20.1/v20.2 目标资源运行窗口的账单对象，必须验证精准结算；如果没有，更新日志必须明确写“仍等待 T+1 账单覆盖”。
- `sentrux gate .` 通过。

如果出现下面任一情况，v20.2 不能宣称“已经完全商业化”：

- OPL chat 仍然没有回复。
- T+1 精准结算还没有用覆盖目标资源的账单对象证明。
- 管理员无法从 ledger、resource、bill evidence 解释用户消费。
