# OPL v20.31 开发方案

目标镜像 tag：`opl-v20.31`
产品基线：`beeb79f feat: ship opl v20.2 commercial ops`
开发基线：当前 `codex/platform-v20` 分支上的 v20.3 工作区

配套 AI 开发实施计划：

## 一、版本定位

v20.31 是 v20.3 的商业化硬化执行版。它不是回退版，也不是新产品线，而是在保留 v20、v20.1、v20.2 已交付能力的基础上，把 v20.3 计划中的 P0 阻断项推进到可测试、可部署、可追责。

必须继承的前序能力：

- v20：套餐订阅、存储权益、周冻结、日扣费、余额宽限、小白导航、`gflabtoken` 登录输入、Secret isolation、OPL upstream 不改动。
- v20.1：资源删除强绑定、删除负向测试、镜像仓库数量约束、必要镜像 tag 策略。
- v20.2：用户账单摘要、管理员客户账务、余额风险、T+1 精准账单 preview/reconcile、OPL 非空消息回复、文件上传下载、资源释放证据、trace/session 证据链。
- v20.3：Portal 登录和状态层稳定性、账务一致性、OPL 文件任务错误契约、跨站连通性、页面真实渲染、售后边界。

## 二、开发目的

v20.31 要解决的问题是商业化运行前的“可信闭环”：

- 稳定性：登录、充值、上传、跑任务、下载、删除停费不能偶发卡死。
- 账务可信：用户账单、管理员客户账务、ledger、audit、T+1 校准必须一致并可解释。
- 错误可理解：用户不能看到 `502`、`kubectl`、`RBAC`、YAML 等技术错误；管理员可以通过 correlationId 查到技术证据。
- 运营聚焦：管理员首先看到谁花了多少钱、谁余额不足、谁资源没释放、哪笔账等待 T+1。
- 证据链完整：一个 run 必须能串起用户、workspace、输入文件、输出文件、账单、trace、服务器释放证据。
- 售后边界明确：余额不足、冻结资金、宽限期、文件保留期、失败不扣费规则必须可展示、可测试。

## 三、顶层结构原则

v20.31 的代码必须继续执行：

- 模块间低耦合：Portal 状态层、账务层、workspace 层、资源开通层、OPL run 层、runner 层、billing aggregator 层只通过明确 API 或结构化 payload 交互。
- 模块内高聚合：账务模块只负责 wallet、ledger、audit；workspace 模块只负责 workspace、storage、file；run 模块只负责状态机、错误码、trace；resource 模块只负责开通、强绑定和释放证据。
- 模块各司其职：展示层不直接写账务；路由层不拼数据库事务；runner 不决定用户扣费；billing 不处理 UI 文案。
- 不用临时补丁：不通过扩大超时、吞异常、旧版本混跑、假数据渲染来掩盖问题。
- 不污染 upstream：`.runtime/one-person-lab-upstream` 继续保持干净。

## 四、Sentrux 使用边界

本轮继续用 Sentrux 辅助写代码，目标是防止结构继续变坏。

- `sentrux check .` 绝对阈值作为长期目标，不作为 v20.31 推进硬门槛。
- 当前检查结果仍低于绝对阈值：Quality 约 `0.66`，modularity 约 `0.65`，未达到 `min_quality=0.69` 和 `min_modularity=0.8`。
- 本轮不降低 `.sentrux/rules.toml`，不保存新 baseline 伪造通过。
- 每个较大改动前后至少运行一次 Sentrux 观察命令，记录是否引入明显结构退化。
- 代码拆分优先遵守领域边界，不为刷分制造无业务意义的小文件。

## 五、交付范围

### P0-1：前序版本继承矩阵

交付：

- 新增 v20.31 继承矩阵，逐条核对 v20、v20.1、v20.2 能力在 v20.31 中仍存在。
- 对每项能力标记验证方式：本地合约、前端渲染、live gate、T+1 gate。
- 对尚不能验证的项目记录原因和恢复命令。

边界：

- 不把旧版本整体回滚作为继承方式。
- 不允许因为修 Portal 登录而删除套餐、账务、强绑定删除或 OPL 消息回复。

### P0-2：Portal 登录和请求快路径

交付：

- `/login` GET/POST、注册页、OPL internal auth 等公开/认证前路由不先触发全量 `currentUser()` 和 `readDb()`。
- `readBody` 增加大小限制、abort 识别和结构化错误，不让客户端断开导致进程崩溃。
- 登录失败返回业务可理解结果，不能 20 秒超时。

边界：

- 不用单纯拉长 timeout 作为解决方案。
- 不吞掉错误；错误必须进入结构化日志或响应。
- 不绕过认证安全校验。

效果：

- 登录页可以快速打开。
- 假账号登录和管理员登录都能快速返回明确结果。
- Portal 容器不会因客户端断开而重启。

### P0-3：Portal 状态写入和账务一致性

交付：

- 请求路径不执行 schema DDL。
- 充值、扣费、退款、补扣走账务事务 API。
- `wallet + ledger + audit` 同一事务边界提交。
- 账务动作带 `idempotencyKey`，重跑不重复扣费。
- orphan audit 扫描脚本能证明没有账务类孤儿事件。

边界：

- 不继续扩大 `writePortalPostgresSnapshot()` 的业务写入范围。
- 不允许 audit 已落库但 wallet/ledger 未落库。
- 不把用户侧账单和管理员侧账单分别计算成两套口径。

效果：

- 用户余额、管理员客户账务、ledger、audit 一致。
- 失败事务完整回滚。
- 可解释每笔充值、预扣、扣费、退款、补扣。

### P0-4：OPL 文件任务 run 状态机

交付：

- bridge 定义稳定 run 成功/失败响应。
- runner 保留 Kubernetes apply/preflight 的结构化错误。
- 错误码覆盖 namespace 不存在、RBAC 不足、manifest invalid、apply failed、upstream 5xx、launch token invalid。
- Portal/OPL 用户界面展示业务文案；管理员详情保留技术证据。

边界：

- 不允许只返回 `502` 或 `String(error.message)`。
- 不允许只直打 runner 证明成功，必须覆盖 Portal -> adapter -> bridge -> runner。
- 不修改 upstream runtime。

效果：

- 文件任务失败时用户知道是否开始计费。
- 管理员能用 correlationId 定位失败阶段。
- 成功任务能上传输入、跑 job、下载输出、写 trace。

### P0-5：跨组件连通性和页面真实渲染

交付：

- `portal.medopl.cn`、`opl.medopl.cn`、`trace.medopl.cn` 全链路健康和业务接口检查。
- Portal -> Postgres、Redis、COS、billing aggregator、resource provisioner、OPL adapter。
- OPL -> runtime bridge -> runner -> Kubernetes。
- Portal/OPL -> Trace 同一 run/session/correlationId。
- Portal 每个关键页面通过浏览器渲染 gate，确认主内容非空、无 console error、无旧版本 payload、无假数据。

边界：

- 不以单个 `/healthz` 代替业务连通性。
- 不以 curl HTML 成功代替前端真实渲染。
- 不把 trace `/healthz` 404 误判为 trace 整体失败；使用实际 public health 和业务查询路径。

效果：

- 每个组件、每个关键接口都有状态、延迟、buildTag、moduleSource、correlationId 证据。
- 能判断是否可以推云，不能推时能说明卡在哪个组件或接口。

### P0-6：资源释放和停止计费

交付：

- 删除服务器继续使用 v20.1 强绑定链路。
- 删除后核对 Kubernetes job/pod/pvc、node pool、CVM instance、resource order billing status。
- 释放失败进入管理员待处理队列，不向用户显示“已停止计费”。

边界：

- 不直接删除当前承载平台 Pod 的 runtime 节点。
- 清理多余测试服务器前，必须确认不是平台组件所在节点，且 resourceOrder/nodePoolId 绑定属于本轮测试资源。

效果：

- 不删错服务器。
- 能证明用户删除服务器后停止新增运行费。

### P0-7：T+1 精准账单

交付：

- same-day E2E 记录 pending 预扣。
- 覆盖 v20.31 run 当日的 T+1 账单对象可用后执行 exact reconcile。
- 精准扣费、退款、补扣、未归因互斥且幂等。

边界：

- preview 不能当最终结算。
- signed URL、临时 token、API key 不进入文档、源码、evidence。
- T+1 未回来时只能标记“待 T+1 终验”，不能宣称最终商业化封版。

效果：

- 用户账单、管理员客户账务、resource order exact cost 三处一致。
- T+1 未归因有原因和处理入口。

- 删除服务器、释放证据、停止计费状态。
- 120 分钟内 pending 账单核对。
- T+1 exact reconcile。

## 七、推云判断

允许推云的前置条件：

- 本地 P0 合约测试通过。
- build/typecheck 通过。
- Secret isolation 检查没有泄露。
- 镜像仓库容量允许覆盖 `opl-v20.31` 或已确认只保留必要镜像。
- kubeconfig 可访问 TKE context。
- 当前线上临时 v19 recovery 状态已明确会被 v20.31 覆盖。

不允许推云的情况：

- Portal 登录本地合约仍失败。
- 账务事务测试仍失败。
- OPL run 错误契约仍失败。
- 构建失败。
- 发现密钥会进入镜像、日志、文档或 evidence。
- 资源清理策略无法确认不会删错平台节点。
