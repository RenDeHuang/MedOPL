# OPL v20.3 开发方案

日期：2026-05-03
目标镜像 tag：`opl-v20.3`
基线提交：`beeb79f feat: ship opl v20.2 commercial ops`

配套 AI 开发实施计划：

- `docs/superpowers/plans/2026-05-03-opl-v20.3-commercial-hardening.md`

## 一、结论

v20.3 的目标不是继续堆新功能，而是把 v20.2 暴露出来的商业化阻断点根治到可以封版验证。

v20.2 已经完成本地提交，但全量 live E2E 没有通过，不能面向小白用户公开商业化上线。v20.3 必须先解决三类失败：

1. Portal Postgres deadlock、登录慢、容器崩溃。
2. 管理员充值后 audit、wallet、ledger 不一致。
3. OPL 文件任务启动失败，`/api/opl-launch/runs` 只返回 502，无法定位 `kubectl apply` 失败原因。

同时，v20.3 必须把商业化最小可卖形态的硬要求写入 gate：

- 稳定性：登录、充值、上传、跑任务、下载、删除停费不能偶发卡死。
- 账务可信：用户和管理员看到的钱必须一致，且能解释每笔扣费。
- 错误可理解：小白不能看到 502、kubectl、RBAC，要看到“任务服务器启动失败，未开始计算，不会继续扣运行费”这类业务解释。
- 运营后台聚焦：管理员首先看“谁花了多少钱、谁余额不足、谁资源没释放、哪笔账等 T+1”。
- 证据链：一个 run 要能串起用户、workspace、输入文件、输出文件、账单、trace、服务器释放证据。
- 售后边界：余额不足、冻结资金、宽限期、文件保留期、失败不扣费规则要明确。

只有这些 P0 关闭后，才允许重新推进 same-day live E2E、T+1 精准账单、删除服务器停止计费和小白商业化体验验收。

## 二、顶层原则

v20.3 必须继续执行以下结构原则：

- 模块间低耦合：Portal 状态层、账务层、工作区层、OPL run 编排、Runner/Kubernetes、资源开通、T+1 账单归因只通过明确接口交互，不共享隐式状态。
- 模块内高聚合：每个模块只负责一个业务聚合。账务模块统一处理 wallet、ledger、audit；工作区模块统一处理 workspace、storage、files；run 模块统一处理 run 状态机、错误码和 trace。
- 模块各司其职：迁移只做迁移，账务只做账务，OPL 网关只做启动和消息代理，资源模块只做强绑定开通/删除，Portal 展示层只做用户和管理员可理解表达。
- 失败可诊断：所有 P0 失败必须带阶段、错误码、correlationId 和审计证据，不能只返回一段不可结构化的异常字符串。
- 商业账务可证明：充值、扣费、退款、补扣必须可重放、可对账、幂等，不能出现 audit 有记录但 wallet/ledger 无记录的状态。

## 三、v20.2 失败复盘

### 1. Portal deadlock 与崩溃

已确认的根因是状态持久化模型会在业务请求中触发大事务和 DDL 竞争。

涉及文件：

- `services/portal/src/state/portal-store.mjs`
- `services/portal/src/state/portal-store-schema.mjs`
- `services/portal/src/state/portal-store-postgres-persistence.mjs`
- `services/portal/src/state/portal-store-postgres-lab-persistence.mjs`

问题点：

- `initializeStorageInfra()` 会调用 `initializePostgresSchema(pool)`，业务读写路径可能触发 `CREATE TABLE IF NOT EXISTS` 和 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`。
- `writePortalPostgresSnapshot()` 在一个事务内写入多个领域，并对 `ledger_entries`、`resource_orders`、`resource_order_events`、`workspace_files`、`user_sandboxes`、`groups`、`portal_settings` 等表做全表删除后重写。
- lab 订阅持久化也存在 `DELETE FROM table` 后整体重写的模式。
- live 现场已经抓到 deadlock 分别出现在 `initializePostgresSchema()` 和 `writePortalPostgresSnapshot()`。

v20.3 解决方向：

- 请求路径不得执行 schema DDL。
- 状态写入从全库快照写改为领域内增量事务。
- 账务、工作区、订阅、资源订单、会话分成独立 store。
- 每个 store 固定写入边界和表顺序，避免跨领域大事务。

### 2. 账务一致性失败

已确认的根因是 audit event 和 wallet/ledger 不在同一个事务边界内。

涉及文件：

- `services/portal/src/routes/admin-user.routes.mjs`
- `services/portal/src/state/portal-store.mjs`

问题点：

- `handleRecharge()` 先改内存 wallet 并 append ledger。
- 然后调用 `logPortalEvent({ type: "wallet_topped_up" })`。
- `logPortalEvent()` 在 `postgres_redis` 模式下会单独写 `audit_events`。
- 最后才调用 `writeDb(db)`。
- 如果 `writeDb()` 因 deadlock 或进程退出失败，就会出现 audit 已写入、wallet/ledger 未持久化。

v20.3 解决方向：

- 新建账务事务 API，由账务模块一次性写 `wallets + ledger_entries + audit_events`。
- 充值、扣费、退款、补扣必须带 `idempotencyKey`。
- 同一个 `idempotencyKey` 重放时，ledger 只出现一次，余额不重复变更。
- 提供孤儿 audit 扫描和修复前审计报告，但修复动作必须走账务事务 API。

### 3. OPL 文件任务启动失败

已确认失败链路：

`Portal -> portal-adapter -> opl-runtime-bridge -> med-autoscience-runner -> kubectl apply`

涉及文件：

- `services/opl-runtime-bridge/src/runtime-bridge-routes.mjs`
- `services/opl-runtime-bridge/src/runtime-bridge-runs.mjs`
- `services/opl-runtime-bridge/src/runner-client.mjs`
- `services/opl-web-gateway/src/launch-client-script.mjs`
- `adapters/med-autoscience-runner/src/server.mjs`

问题点：

- v20.2 live 第三次 E2E 在 `/portal-adapter/api/opl-launch/runs` 返回 502。
- 底层错误摘要是 `kubectl apply -n default -f ...job-*.yaml` 失败。
- `handleRuntimeRun()` 当前失败响应是 `{ ok:false, error:String(error.message) }`，没有阶段、错误码、重试属性和 correlationId。
- runner k8s smoke 直打 runner `/api/runs`，没有覆盖 Portal 到 adapter 到 bridge 到 runner 的完整链路。

v20.3 解决方向：

- 定义 run 状态机和错误契约。
- runner 必须把 `kubectl apply` 的 exit code、stdout、stderr、manifest metadata、namespace、service account、job name 结构化返回给 bridge。
- bridge 必须映射为稳定错误码，Portal/OPL 前端只消费结构化错误。
- 新增全链路 smoke，必须从 Portal/adapter 发起，不允许只测 runner。

### 4. 商业化连通性缺口

v20.2 的测试证明了一部分服务能单独返回，但还没有证明商业链路每一层都真实打通。

必须补齐的连接：

- `portal.medopl.cn` 到腾讯云 Postgres、Redis、COS、TKE/CVM、billing-aggregator、resource-provisioner。
- `portal.medopl.cn` 到 `opl.medopl.cn`：用户 session、workspace session、launch token、provider key、run/message API。
- `opl.medopl.cn` 到 runtime bridge 和 runner：消息回复、文件任务、artifact、状态同步。
- `trace.medopl.cn` 到 Portal 和 OPL：同一个 tenant/workspace/session/run 能被 trace 查到。
- Portal SPA 内每个导航板块到真实 v20.3 API：不得出现空壳页、旧 v20.2 payload、假数据或只渲染静态样例。

v20.3 解决方向：

- 新增跨域连通性矩阵和 live 脚本。
- 每个页面增加 module source 标记，标明连接的是哪个 v20.3 API 和 build tag。
- 增加浏览器渲染验收：页面能加载、数据能显示、按钮能执行、错误能展示业务文案。
- 把“连通性通过”作为部署后 gate，而不是人工目测。

## 四、P0 交付范围

### P0-1：Portal schema 迁移隔离

目标：业务请求路径不再执行 DDL。

交付：

- 新增 `portal-schema-migrator` 模块，只负责 schema 创建、列迁移、schema version 写入。
- Portal 服务启动时只校验 schema version 和 required tables。
- `/login`、`/portal/api/me`、`/portal/api/billing`、`/portal/api/workspace` 不能触发 `initializePostgresSchema()`。
- migration 失败时服务启动失败，并输出具体表名、列名、版本号。

验收：

- 静态合约证明请求路径没有直接调用 schema DDL。
- 并发读写压测期间 Postgres 不出现 `deadlock detected`。
- Portal 容器在 same-day E2E 期间 restart count 为 0。

### P0-2：Portal 状态写入从快照改成领域事务

目标：去掉跨领域全库快照写。

交付：

- 新增 `portal-accounting-store.mjs`：账务聚合。
- 新增 `portal-workspace-store.mjs`：workspace、storage、workspace file、workspace session 聚合。
- 新增 `portal-resource-order-store.mjs`：资源订单和资源事件聚合。
- 新增 `portal-lab-billing-store.mjs`：套餐订阅、套餐事件、存储扩容、每日费用聚合。
- 保留 `readDb()/writeDb()` 作为兼容入口，但 P0 写接口逐步改为领域 store。
- `writePortalPostgresSnapshot()` 只能保留为迁移和兼容读取镜像用途，不能作为普通业务写路径。

验收：

- 充值、创建 workspace、上传文件、创建 storage order、prepare run、resource order 状态更新分别使用对应 store。
- 不再对账务、资源订单、workspace files 执行全表删除后重写。
- 并发 30 分钟内关键路径 P95 达标，无请求堆积到 20 秒以上。

### P0-3：账务原子性和幂等

目标：wallet、ledger、audit event 一次事务内一致。

交付：

- `topupWallet()`：管理员充值事务。
- `chargeWallet()`：套餐费、运行预扣、精准扣费事务。
- `refundWallet()`：T+1 退款事务。
- `makeupChargeWallet()`：T+1 补扣事务。
- 每个账务动作必须带 `idempotencyKey`。
- ledger 增加唯一约束或等价的唯一写入检查，确保重复执行不重复扣费。
- audit event 由账务事务写入，不再由路由单独写入账务类 audit。

验收：

- 故障注入：事务中途抛错时 wallet、ledger、audit 同时回滚。
- 重放同一个 `idempotencyKey`，余额不重复变更。
- orphan audit 扫描为 0。
- 用户账单、管理员客户账务、resource order exact cost 三处同一 run 金额一致。

### P0-4：OPL run 状态机和错误契约

目标：文件任务失败可定位、可审计、可恢复。

成功响应：

```json
{
  "ok": true,
  "run": {
    "runId": "run-id",
    "status": "submitted",
    "jobName": "job-name",
    "namespace": "default",
    "resourceOrderId": "resource-order-id",
    "traceId": "trace-id",
    "correlationId": "correlation-id"
  }
}
```

失败响应：

```json
{
  "ok": false,
  "error": {
    "code": "RUNNER_K8S_APPLY_FAILED",
    "stage": "k8s_apply",
    "message": "任务服务器启动失败，管理员可以用错误编号定位原因。",
    "retryable": false,
    "correlationId": "correlation-id",
    "details": {
      "namespace": "default",
      "jobName": "job-name",
      "manifestPath": "redacted",
      "exitCode": 1
    }
  }
}
```

允许的 stage：

- `resource_order_prepare`
- `runner_workspace_create`
- `runner_submit`
- `k8s_apply`
- `runner_status_sync`

必备错误码：

- `RESOURCE_ORDER_PREPARE_FAILED`
- `RUNNER_WORKSPACE_CREATE_FAILED`
- `RUNNER_K8S_APPLY_FAILED`
- `RUNNER_NAMESPACE_NOT_FOUND`
- `RUNNER_K8S_RBAC_DENIED`
- `RUNNER_MANIFEST_INVALID`
- `RUNNER_UPSTREAM_5XX`
- `LAUNCH_TOKEN_INVALID`

验收：

- 每个错误码有合约测试。
- 任意 run 失败都能通过 correlationId 串起 Portal audit、bridge runAction、runner 错误、trace event。
- OPL 页面展示用户可理解信息，不展示 `kubectl`、YAML、RBAC 等技术细节；管理员详情可见技术证据。

### P0-5：Runner Kubernetes preflight

目标：在创建真实任务前，确定 namespace、RBAC、manifest、service account、image pull 条件满足。

交付：

- `runner-k8s-preflight.mjs`：负责 namespace、service account、RBAC、image pull secret、manifest dry-run 校验。
- `runner-k8s-errors.mjs`：把 kubectl exit code/stdout/stderr 映射为稳定错误码。
- `server.mjs` 只负责 HTTP 装配和调用 preflight/run service。
- `kubectl apply` 前先执行 server-side dry-run。

验收：

- namespace 不存在返回 `RUNNER_NAMESPACE_NOT_FOUND`。
- 权限不足返回 `RUNNER_K8S_RBAC_DENIED`。
- manifest schema 错误返回 `RUNNER_MANIFEST_INVALID`。
- 真实 k8s smoke 连续 10 次创建任务，`k8s_apply` 失败率为 0。

### P0-6：可恢复 live gate

目标：全量 E2E 失败后可以从明确阶段继续验证，并能清楚知道是否产生付费资源。

交付：

- `live-test-v20.3-same-day-e2e.mjs` 拆成阶段：
  - fixture prepare：创建用户、充值、套餐、workspace。
  - portal smoke：登录、账单、workspace、文件上传。
  - opl message：绑定 `gflabtoken`，发送消息并收到回复。
  - opl file run：上传文件、启动文件任务、等待 job 成功、下载输出。
  - resource lifecycle：创建节点/CVM、记录强绑定、删除服务器、确认停止计费。
  - billing pending：当日预扣、120min 运行窗口核对。
  - billing exact：T+1 账单对象可用后执行精确对账。
- 每阶段写 evidence JSON，包含 stage、correlationId、tenantId、workspaceId、runId、resourceOrderId、资源清理状态。
- 失败 evidence 必须写明是否创建了 TKE/CVM/PVC/Job/Pod 和恢复命令。

验收：

- same-day E2E 从创建用户跑到下载输出和删除服务器一次通过。
- 删除后 Kubernetes job/pod/pvc、node pool、CVM instance 检查为 0 或显示明确的非本轮资源。
- 失败时可以只重跑未完成阶段，不重复充值、不重复创建资源、不重复扣费。

### P0-7：T+1 精准账单封版 gate

目标：不能用 preview 代替最终结算。

交付：

- 等覆盖 v20.3 live run 当日的 T+1 账单对象可用后执行 exact reconcile。
- exact reconcile 必须只接受确定性归因：云资源 ID 或 Resource Provisioner 保存的唯一 resource mapping。
- 每条账单进入且只进入一种结果：精准扣费、退款、补扣、未归因。
- 重跑 exact reconcile 不重复 ledger。

验收：

- 用户账单页、管理员客户账务、resource order exact cost 对齐。
- 未归因行有原因和处理入口。
- 更新日志必须写明账单对象日期、执行时间、目标 run/resource order、结算结果。

### P0-8：跨站连通性和真实模块渲染

目标：证明用户看到的页面、按钮和数据都连接真实 v20.3 模块。

交付：

- `live-test-v20.3-connectivity-matrix.mjs`：检查 Portal、OPL、Trace、腾讯云依赖和内部服务连接。
- `smoke-test-v20.3-portal-module-wiring-contract.mjs`：静态检查 Portal 导航、路由、API client 和 payload builder 指向 v20.3 真实模块。
- `live-test-v20.3-portal-rendering.mjs`：浏览器级检查 Portal 每个关键页面正常渲染、无 console error、无空壳数据、无旧版本文案。
- `live-test-v20.3-session-trace-connectivity.mjs`：验证 Portal session、OPL session、Trace run 使用同一个 correlationId/runId。

连通性矩阵至少包括：

- Portal -> Postgres。
- Portal -> Redis。
- Portal -> COS。
- Portal -> billing-aggregator。
- Portal -> resource-provisioner。
- Portal -> OPL adapter。
- OPL web -> runtime bridge。
- Runtime bridge -> runner。
- Runner -> Kubernetes API。
- Runner -> workspace storage。
- Portal/OPL -> Trace。
- Billing aggregator -> COS T+1 object key。

验收：

- 每条连接输出 `ok/status/latencyMs/buildTag/module/source/correlationId`。
- 任一 P0 连接失败，不允许标记 v20.3 可封版。
- 普通用户关键页面不出现空白主内容、旧版本数据、技术错误字符串。
- 管理员关键页面能看到真实客户账务、云资源状态、待处理队列。

### P0-9：小白售后边界和失败不扣费规则

目标：用户遇到余额不足、任务失败、文件保留到期时，能看懂平台如何处理钱和文件。

交付：

- 余额不足状态机：
  - 可用余额充足：允许新任务。
  - 可用余额不足但冻结资金覆盖当前服务周：提醒充值，不停止已承诺服务。
  - 可用余额和冻结资金不足：阻止新付费任务。
  - 宽限期内：允许下载已有输出，不允许新付费任务。
- 文件保留边界：
  - 输入文件、输出文件、删除服务器后的结果保留期。
  - 保留期到期前提醒。
  - 保留期到期后管理员可查审计，不向用户承诺继续可下载。
- 失败不扣费规则：
  - run 未进入 `submitted/running` 前失败，不产生运行费。
  - run 进入 running 后失败，先 pending，最终按 T+1 exact reconcile 校准。
  - 资源释放失败时继续进入待处理队列，不能对用户展示“已停止计费”。

验收：

- 用户账单页和任务失败页用业务语言解释金额状态。
- 管理员能看到每个失败 run 的计费状态、是否可退款、是否待 T+1。
- 售后边界有合约测试和浏览器 smoke。

## 五、P1 交付范围

### 1. 小白新手主路径收口

普通用户只保留主路径：

- 套餐
- 工作空间
- 文件
- OPL 任务
- 账单
- 轨迹
- 删除服务器/停止计费

用户页面不得出现 K8s、TKE、CVM、COS、OpenCost、node pool 等底层术语。存储表达为“文件空间、已用容量、扩容、保留期”。

### 2. 管理员入口合并

管理员主路径收敛为：

- 客户账务与归因：一人一行，能看到余额、充值、今日消费、本月消费、累计消费、待校准、补扣/退款。
- 云资源状态：展示服务器编号、任务编号、resource order、node pool、CVM、Job、PVC、释放证据。
- 待处理队列：余额不足、账单未归因、资源释放失败、OPL key 问题、文件任务启动失败。

`admin/dashboard`、`admin/ops`、`admin/system`、`admin/usage`、`admin/alerts` 中重复的信息应合并到以上三条主线。数据模型不删除，展示层降重。

### 3. Trace 业务证据页

Trace 不再只做通用日志入口，必须能回答：

- 这是谁的任务？
- 属于哪个 workspace？
- 输入文件是什么？
- 输出文件在哪里？
- 对话内容和 run 状态是什么？
- 消耗多少钱？
- 服务器是否已释放并停止计费？

## 八、部署和封版条件

部署 tag：`opl-v20.3`

发布前必须满足：

1. v20.3 本地合约测试通过。
2. Portal 并发稳定性测试无 deadlock。
3. 账务原子性和幂等测试通过。
4. OPL 文件任务全链路 smoke 通过。
5. 跨站连通性矩阵通过，Portal/OPL/Trace/腾讯云依赖均连接真实 v20.3 模块。
6. Portal 浏览器渲染 gate 通过，关键页面无空壳、无旧模块、无 console error。
7. same-day live E2E 跑到下载输出和删除服务器。
8. Portal 容器 restart count 在 live E2E 期间为 0。
9. T+1 exact reconcile 完成，或更新日志明确写“等待覆盖 v20.3 run 的 T+1 账单”，并禁止声明公开商业化上线。

允许状态：

- 如果 P0 全部通过，v20.3 可以进入“受控商业化灰度封版验证”。
- 如果 P0-7 T+1 还未回来，只能标记为“待 T+1 终验”，不能标记为“最终商业化封版”。

不允许状态：

- Portal 登录仍慢到 20 秒级。
- 仍出现 Postgres deadlock。
- audit、wallet、ledger 不一致。
- OPL 文件任务仍只返回 502。
- 不能下载输出文件。
- 删除服务器后无法证明停止计费。
- Portal、OPL、Trace 任一关键 session/run 无法串联。
- Portal 页面仍连接旧 payload、假数据或空壳模块。
- 余额不足、冻结资金、宽限期、文件保留期、失败不扣费规则没有明确展示。

## 九、subagent 评估记录

本方案使用三个只读 subagent 并行评估，均未修改文件，均未输出 secret：

- Portal/账务评估：模型 `gpt-5.3-codex`，结论是 deadlock 来自运行时 DDL 与跨领域全量快照写事务，账务不一致来自 audit 单独落库。
- OPL 文件任务评估：模型 `gpt-5.3-codex`，结论是 run 失败链路已接通但错误契约不足，必须补 run 状态机、错误码、correlationId 和全链路 smoke。
- 商业化 UX/运维评估：模型 `gpt-5.3-codex`，结论是小白商业化的 P0 是稳定主路径、可理解账单、可下载结果、删除停费和可行动错误文案。

## 十、开发顺序

1. 先做 Portal schema 迁移隔离和账务事务 API。
2. 再把充值、扣费、workspace、storage、resource order 写路径迁到领域 store。
3. 再补 OPL run 状态机、错误契约和 runner k8s preflight。
4. 再补跨站连通性矩阵、真实模块渲染 gate 和 session/trace 连通 gate。
5. 再补可恢复 live gate。
6. 最后做用户/管理员信息架构瘦身、售后边界和 Trace 业务证据页。

这套顺序不能反过来。因为 Portal 状态和账务不稳定时，继续跑 live E2E 会重复制造不可信证据；OPL run 错误不可诊断时，继续改前端只会掩盖真实失败阶段。
