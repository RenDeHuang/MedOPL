# OPL v20.33 AI 开发方案

日期：2026-05-04

目标版本：`opl-v20.33`

## 结论

v20.33 的目标不是继续增加功能，而是把 v20.32 已经上传到云端的能力收敛成“小白用户可完成一次任务”的上线版本。Sentrux gate 在本版本不是硬性准入项；结构质量只作为观察指标。真正的上线准入项是体验速度、流程清晰度、真实 full loop 证据、资源删除停费证据、正式入口命中证据和可回滚发布证据。

v20.33 不修改 `https://github.com/gaofeng21cn/one-person-lab`，也不修改本地 `.runtime/one-person-lab-upstream` 上游源码。所有优化只发生在 Portal、Portal frontend、OPL gateway、OPL runtime bridge、resource provisioner、billing aggregator、部署清单和测试脚本。

## v20.33 总则

1. 小白优先：用户不需要理解 TKE、CVM、节点池、COS bucket、trace backend 或 billing tag。用户只看到套餐、存储、实验室、任务结果、费用和删除。
2. 一条主流程：注册或登录、选择推荐套餐、充值、开通存储、创建计算资源、进入 OPL、发消息或跑样例文件、下载结果、查看账单和轨迹、删除资源。
3. 入口统一：用户只使用 `portal.medopl.cn`、`opl.medopl.cn`、`trace.medopl.cn`。内部可以用 v20.33 隔离 namespace 和 transport override 做验证，但不能把测试域名作为用户入口。
4. 体验有硬指标：Portal 登录小于 2 秒，普通页面首屏小于 3 秒，Portal 到 OPL 可见准备页小于 2 秒，OPL 可交互小于 8 秒，OPL 首次回复小于 10 秒。
5. full loop 是生产前硬门槛：必须有 v20.33 真实资源闭环证据，包含创建、使用、下载、账单/轨迹、删除、停费和残留复查。
6. 不做非严谨补救：不通过 sleep、重复刷新、忽略错误、猜测页面状态、手工改订单、手工填云资源 ID、跳过删除证据来让 gate 通过。
7. 版本证据必须是应用证据：不能用 Kubernetes `/version` 或 API server 403/health 作为应用版本证明。应用必须暴露或返回 `opl-v20.33` build tag，并与云上 deployment image tag 对齐。

## 为什么开发

v20.32 已经解决了“能力是否存在”的一部分问题：云端已有 v20.32 镜像，生产前不创建资源验收通过过，OPL 消息验收通过过。但它还不能直接面向小白商业化运营，原因很明确：

- 体验过慢：最近证据中 Portal 页面首屏约 7.1 秒到 22.0 秒，Portal 到 OPL 约 75 秒。
- full loop 未通过：`.runtime/v20.32-isolated-full-loop` 最新记录没有成功闭环，只有 skip 和 failed。
- 用户心智仍复杂：用户需要理解太多资源、账单、trace 和 OPL 登录细节。
- 版本命中证据容易混淆：外部 `/version` 可能落到 Kubernetes API server 语义，不是应用 build 证据。
- 资源删除和停费仍需要完整证据：不能只证明镜像 tag 或页面能打开。

v20.33 要把这些风险压到上线前可接受范围。

## 商业化运营判断

v20.33 完成后，如果以下条件全部满足，可以进入受控商业化试运营：

- v20.33 真实 full loop 通过，证据写入 `.runtime/v20.33-isolated-full-loop/`。
- 删除后节点池、CVM、Pod、Job、PVC、订单计费状态都有复查证据。
- Portal 页面首屏、Portal 到 OPL、OPL 首次回复达到 v20.33 体验指标。
- 用户只需要走推荐套餐主流程，不需要手填云资源 ID 或理解云厂商参数。
- 云上只读核对证明正式入口命中 v20.33 应用实例。
- 回滚命令、镜像 digest、迁移 job、数据备份点已经记录。

受控商业化试运营的含义：

- 可以开放给小规模真实付费用户或试点客户。
- 可以按套餐收款，并用同日资源订单、预扣、删除停费和后台账单证据做运营。
- 需要人工值守发布窗口、资源残留复查和账单复查。

v20.33 完成后仍不等于全面无人值守商业化平台。全面商业化还需要后续版本补齐：

- T+1 COS 精确账单归因自动化对账。
- 用户协议、发票、退款、账务审计报表。
- 告警、SLA、容量水位、异常费用自动冻结。
- 多套餐库存策略和更大规模并发压测。

因此本版本的商业化定位是：可以进入受控商业化试运营；不能宣传为完全自动化、无人值守的大规模生产平台。

## 交付边界

### v20.33 必须交付

- Portal 和 OPL 首屏体验优化。
- 小白推荐套餐主流程。
- OPL 启动准备页和阶段状态。
- v20.33 full loop live gate。
- v20.33 生产前验收 gate。
- 应用 build tag 证明链路。
- 删除停费和云资源残留复查。
- v20.33 发布、回滚、验收文档。

### v20.33 不交付

- 不修改 `https://github.com/gaofeng21cn/one-person-lab`。
- 不修改 `.runtime/one-person-lab-upstream`。
- 不改造 OPL upstream UI 源码。
- 不把 Sentrux 绝对阈值作为上线 blocker。
- 不做 T+1 COS exact reconcile 的全自动闭环。
- 不做多套餐复杂推荐、动态库存竞价或云资源高级配置。
- 不新增用户可见测试域名作为正式入口。

### Step 2：Portal shell 和鉴权快路径

目的：让用户尽快看到页面，而不是等完整 DB 和事件扫描。

开发内容：

- `/portal/app/*` 返回 HTML shell 前只做轻量鉴权，不做完整 `readDb()`。
- `currentUser(req, { mode })` 明确区分 `auth_light`、`shell`、`full`。
- 需要完整用户数据的 API 继续由 API 自己读取，不阻塞 HTML shell。
- 新增时序点：`auth_ms`、`shell_ms`、`full_user_ms`。

涉及文件：

- Modify: `services/portal/src/app/portal-http-dispatcher.mjs`
- Modify: `services/portal/src/app/portal-runtime.mjs`
- Test: `scripts/smoke-test-v20.33-portal-shell-fast-path-contract.mjs`

验收命令：

```bash

```

上线指标：

- 已登录用户访问 `/portal/app/overview` 的 HTML shell 返回小于 800ms。
- 未登录用户跳转登录小于 500ms。

### Step 3：Portal 页面首屏并行化和懒加载

目的：把页面 7 秒到 22 秒的首屏等待压到 3 秒内。

- 管理员告警、usage、trace 等页面拆成首屏 summary API 和详情 API。
- 页面 loading 状态按区域显示，不再全页阻塞。
- 前端 API 层只保留薄 axios 封装，不增加重试、轮询或隐藏等待。

涉及文件：

- Modify: `services/portal/frontend/src/views/overview/OverviewView.vue`

- Modify: `services/portal/frontend/src/views/resources/ResourcesView.vue`

### Step 4：服务端读路径结构化提速

目的：减少全量扫描和大 JSON 读取对页面/API 的拖慢。

开发内容：

- 为 overview、billing、trace、resources 建立明确 payload builder，不在通用页面路径里做全量聚合。
- `readPortalEvents(limit)` 必须按 limit 和事件类型读取，禁止为一个页面读取全量事件后再过滤。
- `collectRunsForUser` 增加按 user/workspace/run 的有界读取路径。
- 对每个 payload builder 输出耗时 breakdown。

涉及文件：

- Modify: `services/portal/src/state/portal-store.mjs`
- Modify: `services/portal/src/app/portal-page-runtime-payloads.mjs`

## 交付标准

v20.33 可以进入受控商业化试运营，必须同时满足：

- 本地合同全部通过。
- 前端 typecheck 和 build 通过。
- `check-one-person-lab-upstream-clean.mjs` 通过。
- v20.33 生产前验收通过。
- v20.33 OPL 消息 live gate 通过。
- v20.33 full loop live gate 通过。
- v20.33 production readiness 通过。
- 删除后残留复查为零。
- 体验指标达标。
- 发布和回滚记录完整。

任何一项不满足，都不能说“v20.33 可商业化生产”。最多只能说“v20.33 局部能力可用”。

## AI 开发执行建议

建议按顺序执行，不要跳 step：

1. Step 0 到 Step 1：先建证据和边界。
2. Step 2 到 Step 4：先把 Portal 卡顿降下来。
3. Step 5 到 Step 6：再把 OPL 进入链路做成可见进度。
4. Step 7：最后收口小白套餐流程。
5. Step 8 到 Step 10：跑真实 full loop、生产前验收和发布。

可并行的 subagent 拆分：

- Worker A，模型 `gpt-5.4`：Portal shell、鉴权快路径、服务端读路径。
- Worker B，模型 `gpt-5.3-codex`：前端首屏、推荐套餐、我的资源体验。
- Worker C，模型 `gpt-5.4-mini`：v20.33 evidence、production preacceptance、message loop 和 full loop 脚本。
- Worker D，模型 `gpt-5.3-codex`：部署、build tag、readiness、回滚记录。

每个 worker 必须只改自己的文件范围，不回退其他人改动。所有 subagent 创建时必须显式记录模型，且只允许 `gpt-5.4`、`gpt-5.3-codex`、`gpt-5.4-mini`。
