## 结论

v20.34 的目标不是继续堆功能，而是把 v20.33 已经能跑通的工程闭环修正成“面向中国小白用户可试运营”的商业化闭环。v20.33 证明了 Portal、OPL、Trace 的生产入口和异步消息 loop 可以工作，但还没有解决商业化放量前最关键的问题：套餐心智混乱、按钮反馈缺失、API key 入口不一致、OPL 回复耗时不可解释、资源/工作空间/账单/轨迹职责重叠、admin 页面带工程验收遗留、测试数据污染运营视图。

v20.34 必须把 P0 和 P1 问题一起纳入版本范围。完成后可以进入受控商业化试运营；不能直接宣称大规模无人值守商业化放量。大规模放量仍需要后续版本补齐支付渠道、法务合规、发票退款、SLA、容量水位和自动客服工单。

## v20.34 总则

1. 小白优先：普通用户不应看到 `tenantid`、`runid`、`serverplanid`、Harbor、OpenCost、Rancher、Langfuse ClickHouse、K8s 这类工程字段或内部系统。
2. 三段商业主流程：选套餐、用工作空间、看账单和轨迹。用户不需要理解资源订单、云资源绑定、trace backend 和计费标签。
3. 套餐要完整：必须展示入门、进阶、自定义三类选择。入门是 `2C / 10GB`，进阶是 `8C / 100GB`，自定义允许用户选择计算和存储规格。
4. 所有按钮必须有反馈：任何可点击动作都要有 loading、成功、失败原因和下一步，不允许“点了没反应”。
5. 计费动作必须幂等：开通、升级、扩容、释放、删除、充值、冻结、provision 都要防重复点击和重复提交。
6. OPL 入口必须统一：`portal.medopl.cn` 和 `opl.medopl.cn` 不能表现出两套 API key 逻辑。普通用户只看到“已连接/未连接”，不被迫理解 provider key。
7. OPL 慢必须可解释：继续保留异步 `202 accepted`，但必须记录消息从 accepted 到后台执行、ACP 调用、持久化、trace 发布的分段耗时。
8. traceId 必须成为 gate：每一次 OPL 消息必须能拿到 traceId，并能在 Trace 入口或 trace API 查到对应记录。
9. 页面职责必须收敛：套餐页管购买和升级；工作空间管文件、结果和进入实验室；我的资源管资源生命周期和停费；账单管钱；轨迹管过程。
10. admin 变运营台：管理员页面必须服务客户支持、账务处理、订单处理、资源异常处理；工程验收入口退出主界面。
11. 测试数据必须隔离：`test-*.example.test`、live/e2e 夹具、内部测试订单不能污染商业经营指标。
12. 上游不动：不修改 `https://github.com/gaofeng21cn/one-person-lab`，不修改本地 one-person-lab upstream，只通过 Portal、Gateway、Runtime Bridge、Adapter 做集成。

## 目的

v20.34 的直接目的：

- 让中国小白用户可以在 Portal 中清楚完成套餐选择、开通、进入工作空间、进入 OPL、收到回复、查看轨迹、理解账单、释放资源。
- 让运营人员可以判断用户、订单、资源、账务、trace 的真实状态，而不是在工程监控面板里猜。
- 让每一次商业化关键动作都有可复跑证据，包括 UI 点击、API 响应、错误文案、traceId、计费状态和资源状态。
- 让后续商业化试运营可以基于证据决策，而不是基于“页面能打开”的主观判断。

## subagent 只读扫描结论

所有 subagent 均为只读扫描，模型均记录为 `gpt-5.3-codex`。

1. 普通用户侧：`/packages`、`/resources`、`/workspace`、`/billing`、`/trace` 均有明确可点击控件，但套餐开通、存储扩容、进阶升级缺 success/error UI；工作空间仍含存储购买入口；资源页删除并停费属于最高风险动作。
2. OPL trace：Runtime Bridge 已有 `traceLinks` 和 `/api/trace-links`，但 launch、session bind、message、run 没有强制共用同一个 root traceId；message status 当前也没有直接返回 traceId，无法作为 gate。
3. admin IA：`AdminSystemView` 和 `AdminOpsView` 同源重复，都裁剪自 `buildAdminOverviewPayload(db)`；Harbor、OpenCost、Rancher 仍在主状态结构中；腾讯云真实资源源 `/portal/api/cloud/resources` 已存在，但没有成为 admin 主展示。
4. 测试体系：v20.33 component-response 脚本只采样 `button,[role=button]`，默认上限 3 个，且有 mutation 关键词过滤；它不能证明“每个组件都点击尝试”。v20.34 必须新增全量组件点击矩阵。

## P0 范围

### P0-1：traceId gate

目的：证明每条 OPL 消息不仅能返回回复，还能被追踪和排查。

开发要求：

- 消息 accepted 响应必须包含或可查询到 `messageId`、`runId`、`traceId`、`statusUrl`。
- launch、session bind、message、run 必须继承同一个 root traceId。
- `statusUrl` 最终状态必须包含 trace 关联字段。
- live gate 必须访问 Trace 入口或 trace API，断言 traceId 可查。
- evidence 文件必须记录 trace 查询耗时和结果。

- 未订阅时不能直接扩容，要明确提示“请先开通套餐”。

## 开发顺序

1. 冻结 v20.34 基线：确认 worktree、branch、Sentrux baseline、上游 clean。

3. 补 smoke 合同：traceId、套餐三档、组件点击矩阵、入口统一、测试数据隔离、租户隔离。

6. 改普通用户页面职责：我的资源、工作空间、账单、轨迹。
7. 改 admin 信息架构：客户账务、账单归因、云资源状态、系统状态。
8. 增加全量点击自动化，在生产只做安全点击，在 staging/mock 做提交类动作。
9. 跑 Sentrux gate、Portal check、frontend typecheck/build、smoke tests。
10. 部署 v20.34 到云端，跑 production preacceptance、component click matrix、Portal->OPL->Trace gate。
11. 输出商业化放量报告，明确 `not-approved`、`controlled-trial` 或 `paid-ramp`。

### 全量组件点击测试

点击范围：

- 普通用户：总览、套餐、我的资源、工作空间、OPL 入口、账单、轨迹。
- 管理员：运行总台、用户、分组、工作空间详情、运行详情、客户账务、账单归因、告警、系统状态、云资源状态、沙箱、审计。
- 公共组件：侧边栏、顶部栏、弹窗、tab、筛选、表单、详情链接、返回链接。

点击策略：

- 只读动作：生产真实点击。
- 计费动作：生产只点到报价或二次确认，不直接提交；staging/mock 才提交。
- 危险动作：生产只验证二次确认出现，不确认删除；staging/mock 才确认。
- OPL 消息：使用隔离测试用户和明确测试标记，必须记录 traceId。
