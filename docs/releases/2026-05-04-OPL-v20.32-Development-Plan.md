# OPL v20.32 Development Plan

日期：2026-05-04

目标版本：`opl-v20.32`

## 结论

v20.32 只做最小商业闭环，不再把 T+1 精确账单对账作为上线前 blocker。这个版本要证明一件事：小白用户在 Portal 里选择套餐，Portal 负责开通对应算力和存储，随后用户能在 Portal 看到“我开了什么”，并且点击删除时只按订单删除对应资源。

最小分账标签固定为：

- `resourceorderid`
- `runid`
- `serverplanid`
- `tenantid`
- `workspaceid`

## 为什么开发

当前问题不是上游 OPL 不存在，而是商业 Portal 没把 OPL、套餐、资源订单、存储订单、删除动作统一成普通用户能理解的闭环。用户不应该自己选择 CVM 节点池、手填云资源 ID 或理解账单明细字段。Portal 必须把上游 OPL 当作实验室执行面，把腾讯云资源当作受订单约束的后台资源，并把两者绑定到同一个用户、workspace、run 和订单。

如果这个闭环不成立，就算云账单已经能下载，也只能证明“云上发生过消费”，不能证明“哪个用户因哪个 run 开了哪些资源、能否由用户自己删除、删除是否精确命中同一组资源”。

## 开发目的

v20.32 的交付目标：

1. Portal 面向小白展示两个固定套餐和一个自定义入口。
2. 套餐可以叠加存储和计算节点，不要求用户理解云厂商规格。
3. Portal 与 OPL 统一账号和统一入口，`opl.medopl.cn` 必须能真实收到消息并返回结果。
4. 用户资源页按订单展示绑定关系：`tenantId`、`workspaceId`、`runId`、`resourceOrderId`、`serverPlanId`、节点池、CVM、存储前缀。
5. 删除入口只提交 `resourceOrderId` 和确认项，后端从订单绑定解析节点池、CVM、存储，不接受前端手填云资源 ID 来决定删除目标。
6. 账单侧只保证最小标签齐全，为后续 COS 分账账单对账提供稳定关联键。

## 怎么开发

### 后端资源绑定

新增独立领域模块 `services/portal/src/domain/user-resource-bindings.mjs`，只负责把已有订单和存储记录合成用户视图：

- 输入：`db`、`user`。
- 依赖：`resource-orders`、`workspace-storage` 的公共函数。
- 输出：普通用户可读的绑定项。
- 不直接调用腾讯云，不直接写 DB。

新增公共 API：

- `GET /portal/api/my/resources`

返回字段至少包括：

- `tenantId`
- `workspaceId`
- `runId`
- `resourceOrderId`
- `serverPlanId`
- `nodePoolId`
- `cvmInstanceIds`
- `storageOrderId`
- `cosPrefix`
- `status`
- `canDelete`
- `deleteBlockedReason`
- `billingTags`

### 强绑定删除

收敛 `POST /portal/api/resource-orders/delete-node-pool`：

- 前端只传 `resourceOrderId`、`confirmDeleteNodePool`、`destroyCvmInstances`。
- 如果 payload 里带 `nodePoolId` 或其他云资源 ID，后端拒绝，避免用户或前端错误删除别人的资源。
- 后端必须从订单绑定中解析 `nodePoolId`。
- 订单不属于当前用户、订单缺少节点池、绑定不完整时拒绝。
- 删除成功后把订单转为 `released`，记录删除事件和 provisioner 返回证据。

### 套餐与 Portal 页面

保留普通用户入口：

- 总览
- 套餐
- 我的资源
- 工作空间
- 账单
- 轨迹

云服务器商品目录继续保留为管理员高级页，不作为小白主流程。

套餐页改成：

- 入门套餐
- 进阶套餐
- 自定义套餐入口
- 加 100GB 存储
- 加一个计算节点
- 进入 OPL 实验室

新增或改造“我的资源”页：

- 显示每个资源订单绑定了什么资源。
- 显示最小分账标签。
- 用户点击删除只会调用 `resourceOrderId` 删除。

### Portal 到 OPL 消息

新增 v20.32 live gate：

- 登录 Portal 或沿用已有 OPL 登录链路。
- 打开 `opl.medopl.cn`。
- 发送一条真实消息。
- 验证收到非空回复。
- 记录首字节和完整回复延迟。
- 证据 JSON 不输出密钥、cookie、signed URL。

Sentrux：

```bash

```

Sentrux 结果只作为结构观察，不作为 v20.32 gate。开发过程中必须避免新增跨模块耦合：绑定聚合在 domain，HTTP 装配在 routes，前端只调用 API。

Live gate：

```bash
RUN_V20_32_LIVE=1 node scripts/live-test-v20.32-portal-opl-message-loop.mjs
```

隔离完整闭环 gate：

```bash
RUN_V20_32_FULL_LOOP=1 \
V20_32_ISOLATED_TRANSPORT_CONFIRMED=1 \
V20_32_CONNECT_HOST=<v20.32 isolated ingress or proxy host> \
V20_32_CONNECT_PORT=443 \
V20_32_CONFIRM_DELETE=1 \
V20_32_PORTAL_BASE_URL=https://portal.medopl.cn \
V20_32_OPL_BASE_URL=https://opl.medopl.cn \
V20_32_EXPECTED_BUILD_TAG=opl-v20.32 \
node scripts/live-test-v20.32-isolated-full-loop.mjs
```

该 gate 使用固定正式 host，但必须通过 `V20_32_CONNECT_HOST` 指向 v20.32 隔离入口，并先校验 Portal `/healthz` build tag 为 `opl-v20.32`，避免误打旧线上版本。不要新增或修改 DNS。

## 交付边界

### v20.32 必须交付

- 套餐化入口清晰。
- 用户资源绑定 API。
- 用户资源绑定页面。
- 删除只按订单执行，禁止前端传云资源 ID 决定删除目标。
- 最小分账标签随绑定项和删除请求链路稳定存在。
- Portal 到 OPL 真实消息测试脚本。

### v20.32 不交付

- 不做 T+1 COS 分账账单 exact reconcile。
- 不承诺线上已经是 v20.32，除非完成 build/push/rollout/live gate。
- 不自动删除平台节点或 runtime 节点。
- 不把管理员云资源商品目录暴露给普通小白用户。
- 不支持用户手填 CVM、节点池、COS bucket 来绑定资源。
