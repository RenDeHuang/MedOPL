# OPL v20.32 Cloud And Production Readiness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the non-T+1 gates for v20.32: cloud readiness, fixed-host isolated live loop, and production readiness.

**Architecture:** Keep cloud preflight as a read-only script, keep live commercial-loop mutation behind explicit opt-in flags, and keep production readiness as an evidence evaluator. T+1 COS exact attribution is intentionally excluded from this plan.

**Tech Stack:** Node.js ESM scripts, Kubernetes `kubectl` read-only checks, Docker daemon read-only checks, existing Portal/OPL HTTP contracts, Sentrux structural observation.

---

## Why

v20.32 already has the key Portal business model in code: packages, user resource binding, order-bound deletion, storage billing stop, OPL message/file/download, and five fixed billing tags. The remaining risk is operational: proving the cloud target is ready, proving v20.32 can be exercised without accidentally hitting the old online build, and defining what evidence is required before calling it production.

The user has fixed the DNS boundary: production hosts stay `portal.medopl.cn`, `opl.medopl.cn`, and `trace.medopl.cn`. We must not require `portal-v20-32.*` or `opl-v20-32.*` DNS. Isolation must come from an explicit transport path plus a v20.32 build-tag check.

## Scope

Included:

- Read-only v20.32 cloud readiness script.
- Static contract for that readiness script.
- Update v20.32 live gates to use fixed official hosts plus isolated transport confirmation.
- Production readiness script that evaluates live evidence and production entry health.
- Static contract for production readiness.
- Documentation updates that say T+1 exact COS attribution is deferred.

Excluded:

- T+1 COS exact attribution and settlement.
- Creating, deleting, patching, applying, or rolling out cloud resources from the readiness script.
- DNS changes.
- Declaring production readiness without full-loop evidence and production build evidence.

## Task 1: Cloud Readiness

Files:

- Create `scripts/smoke-test-v20.32-cloud-readiness-contract.mjs`.
- Create `scripts/check-v20.32-cloud-readiness.mjs`.

Steps:

- [ ] Write the static contract first.
- [ ] Run it and verify it fails because the readiness script is missing.
- [ ] Implement the readiness script with only read-only commands.
- [ ] Verify the contract passes.

The readiness script must check:

- v20.32 tag and rendered directory are explicit.
- env file is not git tracked unless it is an example.
- `TCR_PASSWORD` or `TCR_SECRET` is present, with `TCR_SECRET` mapped only inside the readiness check.
- Docker daemon is reachable by `docker --version` and `docker info`.
- `kubectl` can run `version --client`, `config current-context`, `cluster-info`, `get ns`, `get nodes`, and `auth can-i`.
- No command mutates cloud state.
- official hosts remain `portal.medopl.cn`, `opl.medopl.cn`, and `trace.medopl.cn`.
