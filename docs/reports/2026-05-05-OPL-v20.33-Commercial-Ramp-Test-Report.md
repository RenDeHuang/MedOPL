## Root Cause Notes

The Portal jump failure from the earlier run is not the current production state. The latest L3 and L4 evidence show the redirect reaches `https://opl.medopl.cn/`; the test script was hardened to wait for the OPL host and record `finalUrl`.

The Portal component test failure was caused by stale required-text assertions and unstable login/capture timing. The corrected component test uses browser login, waits for the actual page title, records 22 page coverage, and distinguishes mounted runtime components from unused source components.

The L5 blocker is not a cluster availability issue: the production deployment is Ready and `resource-provisioner-opl` is running. The failed-window read-only audit found a frozen order and preauth ledger residue, but the residue order was created by the freeze fallback path with idempotency key `resource-order-freeze-quote:...` and has empty `runId`. This localizes the failure to Portal order identity consistency before provisioning.

Root cause fixed in code: `POST /portal/api/resource-orders/freeze` previously accepted an explicit `resourceOrderId`, but if that order was not visible in the current DB snapshot it silently created and froze a replacement order. L5 then kept provisioning the original quote order id, which could produce `resource_order_not_found` at `/portal/api/resource-orders/provision` while leaving the replacement order frozen. The route now returns `404 resource_order_not_found` when an explicit order id is missing, and the L5 script now records `freezeResourceOrderId` and stops at `resource_freeze_order_id_mismatch` if quote/freeze identities diverge.

The full L5 was not rerun after this fix to avoid creating additional real cloud resources and billing state before the existing frozen/preauth residue is cleaned up.

2. Deploy the freeze identity-consistency fix and rerun L5 in a monitored cost window.
