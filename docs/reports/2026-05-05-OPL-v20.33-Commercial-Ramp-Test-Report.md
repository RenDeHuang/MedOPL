## Root Cause Notes

The Portal jump failure from the earlier run is not the current production state. The latest L3 and L4 evidence show the redirect reaches `https://opl.medopl.cn/`; the test script was hardened to wait for the OPL host and record `finalUrl`.

The Portal component test failure was caused by stale required-text assertions and unstable login/capture timing. The corrected component test uses browser login, waits for the actual page title, records 22 page coverage, and distinguishes mounted runtime components from unused source components.

The L5 blocker is not proven to be a cluster availability issue: the production deployment is Ready and `resource-provisioner-opl` is running. The failure is currently localized to Portal provisioning route execution returning 404 after quote/freeze succeeded. The full-loop script now records a `resource_order_visibility` stage before provisioning and attaches that visibility snapshot to the provision stage, but the full L5 was not rerun to avoid creating additional real cloud resources and billing state.

## Commercial Ramp Position

Do not start paid public ramp yet.

Allowed next use: internal QA, founder-led demos, controlled live verification with no uncontrolled user spend, and read-only monitoring.

Required before paid ramp:

1. Audit and clean the frozen L5 test order / preauth hold from the failed `2026-05-04T23-56-28-178Z` run.
2. Root-cause and fix the `resource-orders/provision` 404 using a non-mutating diagnostic first, then rerun L5 in a monitored cost window.
3. Confirm provisioned resource appears in Portal resources, OPL run can use it, artifacts return, trace remains visible, resource release/delete stops pending cost, and T+1 billing attribution lands.
4. Decide whether `AnnouncementDialog(overview)` and `ChartCard` should be mounted or removed. Until then, the mounted UI passes, but not every source component has runtime response evidence.
