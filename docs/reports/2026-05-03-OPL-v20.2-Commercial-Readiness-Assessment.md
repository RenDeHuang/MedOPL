# OPL v20.2 商业化上线评估

日期：2026-05-03
时区：Asia/Shanghai
目标版本：`opl-v20.2`
评估范围：`portal.medopl.cn`、`opl.medopl.cn`、`trace.medopl.cn`

## 总结论

v20.2 现在不建议面向小白公开商业化上线。

它可以继续作为“内部演示 / 受控灰度 / 人工辅助试运营”的工程底座，但前提是运营人员明确知道：Portal 当前有 Postgres deadlock 和登录慢/崩溃风险，OPL 文件任务 live E2E 未跑通，2026-05-03 的 T+1 精准账单未完成最终扣费、退款、补扣。

如果按“一个小白用户能自助购买、充值、上传文件、跑任务、下载结果、看懂账单、删除服务器并停止扣费”的标准看，v20.2 还没有达标。

## Office Hours 判断

按 `$gstack-office-hours` 的产品诊断视角，当前最关键的问题不是“功能有没有堆出来”，而是“小白是否能放心付钱并理解结果”。

- 真实需求：用户要的是可预测的实验室服务，不是云控制台。
- 最小可卖形态：必须先做到一条稳定的新手路径，而不是让用户在套餐、workspace、账单、trace、K8s 运维之间自己理解。
- 具体痛点：用户要能回答“买了什么、能做什么、用了多久、花了多少钱、为什么扣费”。
- 当前缺口：Portal 稳定性和账务一致性没有过关；OPL 文件任务链路未闭环；trace 还不是一页式业务证据链。
- 合理商业边界：可以做人工看护的灰度试运营，不应公开承诺全自助商业化。

## 是否可以商业运营

### 公开面向小白收费上线

结论：不建议。

原因：

- Portal 登录和状态读写不稳定，商业入口本身不可靠。
- 账务一致性存在现场反例：audit event 显示充值，但 wallet/ledger 查询未对齐。
- OPL 文件任务 live E2E 未跑通，用户上传文件后跑任务和下载输出没有闭环证据。
- T+1 精准账单未覆盖 2026-05-03 v20.2 live run。
- 用户侧还不能在一个地方完整理解购买、使用、费用、结果和删除后的状态。

### 受控灰度 / 人工辅助试运营

结论：可以谨慎保留，但必须降级为“受控验证”，不能承诺完全自助。

前提：

- 每个新客户由管理员人工建档、人工充值、人工确认账单。
- 每天检查 Portal restart、Postgres deadlock、ledger 和 wallet 对账。
- OPL 文件任务失败时有人工处理预案。
- 账单最终金额以 T+1 exact reconcile 为准，用户侧明确展示“等待校准”。
- 不让普通用户看到 K8s、OpenCost、对象存储开通等技术入口。

## 面向小白的体验评估

### 买了什么

部分达标。

套餐页和账单页已经在往“入门套餐、包含存储、每日扣款、周冻结、扩容”方向表达，比云资源术语更接近小白语言。

不足：

- 还没有形成首页级的一句话总结，例如“你当前买的是入门实验室，每天 X 元，包含 10GB 文件空间和小型任务服务器”。
- 工作空间里仍有技术词残留，例如“对象存储开通”这一类表达不应出现在普通用户路径。

### 能做什么

部分达标。

用户能看到 workspace、上传文件、进入 OPL、查看账单和轨迹这些入口。

不足：

- 文件任务 live run 没通过，不能向用户承诺“上传文件后一定能跑出结果并下载”。
- 失败解释不够产品化。现在的真实错误是 adapter 502 和 kubectl apply 失败，小白看不懂，需要翻译成“任务服务器启动失败，管理员正在处理，未开始计算不应继续计费”。

### 用了多久

未完全达标。

运行时间和会话时间散落在 workspace、账单、trace、admin 视图中，没有一个普通用户一眼能懂的“本次任务用了 X 分钟，本月已用 Y 分钟”。

### 花了多少钱

部分达标但不能封版。

账单模块有余额、冻结、今日/本月/累计消费、充值记录、运行中预扣和 T+1 校准的结构。

阻断：

- 本轮出现充值事件与 wallet/ledger 不一致的现场证据。
- 2026-05-03 T+1 精准账单未完成。
- 没有同一条 E2E 证明“跑任务 -> 预扣 -> 删除服务器 -> 停止计费 -> T+1 校准”。

## 功能重叠和残留

### 对象存储开通

普通用户侧不应该继续叫“对象存储开通”。

建议：

- 用户侧只保留“文件空间、已用容量、扩容、保留期”。
- 后端 `storageOrders`、COS key、workspace file metadata 继续保留给审计和账单归因。

### 运行总台

对管理员有价值，但不应作为商业化主叙事入口。

问题：

- 它和客户账务、计费运维、轨迹、云资源状态有重叠。
- “关键入口”和“告警概览”容易把管理员注意力打散。

建议：

- 普通用户完全不展示。
- 管理员侧降权，合并到“客户账务”和“云资源状态”两条主线。

### 告警列表

保留是合理的，但只能保留需要行动的事项。

应该保留：

- 余额不足。
- 充值或扣费异常。
- T+1 账单未归因。
- 资源释放失败。
- OPL key 缺失或无效。
- 文件任务启动失败。

不应该保留：

- 泛泛的系统状态展示。
- 用户不需要处理的云平台内部警告。

### 计费运维里的待处理记录和成本构成

目前还不够面向运营。

用户想看的不是“成本构成”，而是：

- 今天花了多少。
- 本月花了多少。
- 总共花了多少。
- 充值了多少。
- 哪一笔还在等 T+1 校准。
- 哪一笔需要补扣或退款。

管理员想看的是“一人一行”的客户账务，再点进去看 ledger 明细。当前 v20.2 有这个方向，但本轮账务一致性没有过关，不能用于公开商业运营。

### K8s 运维与分发

对小白无用，应该隐藏。

建议：

- 普通用户侧完全移除。
- 管理员侧改名为“云资源状态”。
- 展示服务器编号、任务编号、CVM 编号、节点池编号、是否仍存在、是否停止计费、释放证据。

## Trace 和运营排障

Portal 已经可以形成 workspace/session/run 的轨迹索引，并能关联部分文件和费用摘要。

不足：

- 用户侧不是完整对话复盘页。
- 管理员侧不是“一页式证据链”。
- `trace.medopl.cn` 更像 Langfuse 通用入口，缺少 Portal 业务上下文。

建议：

- 建一个 run/session 详情页，把消息正文、输入文件、输出文件、账单、资源状态、释放证据放在同一页。
- Portal trace 页增加 runId 筛选。
- 管理员从 trace 能一键跳到账单明细、文件列表、资源释放证据。

## 当前 P0 阻断清单

1. Portal Postgres deadlock 和容器崩溃。
2. Portal 登录和 `readDb()` 路径慢响应。
3. 管理员充值、wallet、ledger、audit event 一致性未过现场验证。
4. OPL 文件任务启动失败，`kubectl apply` job YAML 返回错误。
5. 全量 live E2E 未跑通到下载输出、删除服务器、停止扣费。
6. 2026-05-03 T+1 精准账单未完成最终扣费/退款/补扣。
7. Trace 不是完整业务排障证据链。
8. 管理员侧存在运行总台、K8s 运维、计费运维等重复入口。

## 建议上线口径

当前可以说：

- v20.2 已部署到云端。
- OPL 消息回复 live gate 曾通过，runtime URL 保持 `https://github.com/gaofeng21cn/one-person-lab`。
- COS `2026-05-02` object key 账单 preview 可用。
- Portal 产品语义比 v20.1 更接近小白商业化。
- Sentrux regression gate 曾通过，`sentrux check` 绝对阈值本轮先不作为上线 blocker。

当前不能说：

- 可以面向小白公开商业化运营。
- 全量云端 E2E 已通过。
- 用户上传文件、跑任务、下载输出已在 v20.2 live 中闭环。
- 2026-05-03 v20.2 live run 已完成 T+1 精准结算。
- Portal 账务链路已经稳定可靠。

## 下一步最小修复路径

1. 修 Portal Postgres deadlock：迁移 DDL 从请求路径移出，缩小 `writePortalPostgresSnapshot()` 大事务，按表固定写入顺序，补并发写测试。
2. 修 Portal 账务一致性：充值必须在 wallet、ledger、audit event 三处事务一致，失败要可重试且幂等。
3. 修 OPL 文件任务：把 `kubectl apply` 失败原因打印成结构化错误，验证 job yaml、RBAC、namespace、image、volume、label。
4. 重跑全量 same-day E2E：必须跑到输出下载、删除服务器、停止计费。
5. 等 2026-05-03 T+1 账单对象可用后跑 exact reconcile。
6. 瘦身普通用户和管理员导航：普通用户只保留套餐、工作空间、账单、轨迹；管理员聚焦客户账务和云资源状态。
