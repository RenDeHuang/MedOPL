# Portal + OPL 商业化 SaaS V8 AI 开发任务清单

## 背景

本轮 v8 的目标，不是再补一层工程联调说明，而是把 Portal + One Person Lab 变成可对外交付、可计费、可追溯、可维护的商业化 SaaS 控制面。

当前已经具备一部分入口、launch、账单和运行链路基础，但还没有完全闭合到正式商业化所需的状态。v8 要补的，不是“能跑”，而是“客户看得懂、选得明白、扣得清楚、追得回来、拆得开、挂了不互相拖累”。

## 顶层原则

- 模块内高聚合：身份、费用、服务器、运行、存储、trace 各自收敛在自己的模块内。
- 模块间低耦合：模块之间只通过 ID、短期 token、只读状态和明确的 API 协议通信。
- 互不影响：Portal、Gateway、Billing、Runner、Storage 任一模块出问题，不应拖垮其他模块的主路径。
- 易维护：目录、标签、状态字段、错误页、健康检查和回填路径都必须可读、可追踪、可替换。

## 已核查事实

- 已核查到本地 v7 与云上 v7 的相关镜像 digest 一致，说明“镜像内容不同”不是当前差异的主要来源。
- 更可能造成差异的，是运行配置、TKE manifest、Ingress、ConfigMap、Secret、启动顺序和旧进程残留。
- 因此，v8 的核查重点应放在“运行态合同”和“部署态合同”，而不是继续猜镜像。

## v8 本地收口结论

- 服务器与费用：已做到客户选择 `server_plan` 后，Portal 把选择保存到任务空间，launch/runtime/runner 按同一 plan 生成 Job 资源、标签、runtimeClass、nodeSelector、tolerations。当前不是自动创建腾讯云 CVM 或新 TKE 节点；如果老板要“客户点了就自动扩容节点池/买云主机”，下一版需要独立的 `resource-provisioner` 模块。
- OPL 原生登录：已支持 Portal 本地账号密码走 OPL 原生登录框，包括 OpenWebUI 常见的 `/api/v1/auths/signin` 和 `/api/v1/auths/` 合同。OIDC 账号没有本地密码 hash 时，不能凭空用“同一密码”登录，正确路径仍是 Portal/OIDC 登录后 launch。
- 商业准入：进入工作台不再由余额裸值拦截；启动收费 run 由 wallet + trial credit 共同判断。余额和试用都没有时，才阻止新 run。
- 部署态：v8 需要构建的镜像 tag 已渲染为 `opl-v8`；上游 `opl-web-opl` 和动态 runner 镜像保持 `opl-v1`，因为本轮没有改它们的源码。
- 账单真实源：价格和账单仍由 `billing-aggregator` 聚合腾讯云价格/账单 API；没有腾讯云 Secret 时，本地只能验证合同和 UI，不能证明真实账单可拉取。

## 1. 服务器与费用商业化

### 目的

让客户透明选择服务器规格和价格，并且在选择之后，平台真的能按所选规格在集群里开通或调度对应资源。

### 商业化逻辑

客户应先看到“可售规格、地域、价格、冻结金额、价格来源”，再决定是否开通。平台不应该把价格藏在后端，也不应该把云厂商的复杂实例族直接暴露给客户。前台展示的是商品，后台执行的是云资源映射。

### 实现方式

- `server_plans` 维护可售 SKU 白名单，而不是把所有云厂商实例全量暴露给用户。
- `billing-aggregator` 提供价格来源、更新时间和预扣依据。
- Portal 负责服务器选择、价格展示、冻结提示和下单入口。
- Runner / Orchestrator 负责把所选 `serverPlanId`、`region`、CPU、内存、GPU、磁盘和调度约束落实成 Job 资源。
- 动态 Job 必须带上 `tenant_id`、`workspace_id`、`run_id`、`server_plan_id`、`region` 等标签，方便账单和审计回收。

### 测试方法

- 选定某个 server plan 后，检查生成的 Job 资源是否与 plan 一致。
- 检查调度约束、节点选择和资源上限是否和选择页面一致。
- 检查价格来源、更新时间和冻结金额是否能回溯到同一 SKU。
- 检查运行结束后的费用能否回到同一个 tenant/workspace/run。

### 交付标准

- 客户可以透明选服务器和价格。
- 选择后，平台能把资源真正落实到集群 Job。
- 账单最终可以回补到腾讯云真实账单。
- 任何价格都能说明来源，任何扣费都能说明依据。

### 当前 v8 是否达到

- 未达到。

## 2. Portal 总览商业化简洁

### 目的

把首页从说明书改成商业化控制台，让用户打开后第一眼就知道自己还能做什么、余额还有多少、最近发生了什么、下一步去哪里。

### 商业化逻辑

商业化首页承载的是转化和操作，不是工程解释。用户不需要知道内部有 adapter、manifest、launch token 或 Gateway 代理细节；用户只需要知道能不能进工作台、能不能继续跑、钱够不够、最近是否有任务、费用是否正常。

### 实现方式

- 收敛首页文案，删除长段内部说明。
- 保留账户、余额、试用、工作台入口、最近运行、今日费用、服务器规格概览。
- 普通用户不展示内部实现词，不展示过多告警，不展示工程验收信息。
- 管理员态可以单独看到 billing 配置、价格来源和运维状态。

### 测试方法

- 首屏扫一遍，不能像说明书。
- 普通用户不应该看到过多内部架构词。
- 页面在桌面和移动端都要保持清楚的主操作入口。
- CTA 应该直接对应“进入工作台”“查看费用”“继续运行”。

### 交付标准

- 首页足够简洁，像 SaaS 控制台。
- 用户不需要读内部说明就能开始操作。
- 页面不暴露多余工程细节。

### 当前 v8 是否达到

- 未达到。

## 3. v7 本地与云端差异核查

### 目的

先把“同一个 v7 为什么本地和云上表现不一样”说清楚，再继续推进 v8。没有这一步，后续所有联调都可能被错误归因。

### 商业化逻辑

正式商业化发布不能只看镜像 tag，要看镜像、配置、入口、上游进程和健康检查是否共同构成同一个运行合同。对客户来说，版本一致但行为不同，是不可接受的。

### 实现方式

- 固定镜像 digest 作为版本证据。
- 对比 TKE manifest、Ingress、ConfigMap、Secret、环境变量、上游进程版本和启动时间。
- 把运行态关键字段写入健康检查和状态页。
- 在文档中明确“镜像一致，不代表运行态一致”。

### 测试方法

- 对比本地和云上的镜像 digest。
- 对比同 tag 的 manifest 和运行参数。
- 对比实际健康检查和 API 响应。
- 确认差异来自配置或旧进程，而不是镜像内容。

### 交付标准

- 能明确说明本地与云上差异的来源。
- 后续排查可以直接看配置和运行态字段，不再靠猜。

### 当前 v8 是否达到

- 核查层面已达到。
- 根治层面未达到。

## 4. OPL 原生登录框使用 Portal 账号密码

### 目的

让用户在 OPL 原生登录框也能用 Portal 账号密码登录，避免两套身份系统割裂。

### 商业化逻辑

用户不应该在 Portal 能登录、到了 OPL 原生页面却说账号无效。商业化产品的入口必须连续。正确做法不是同步密码 hash，而是让 Gateway 成为认证桥，让 OPL 只接受 Portal 认证后的结果。

### 实现方式

- Gateway 拦截 OPL 原生登录请求。
- Gateway 把登录凭证转给 Portal 认证服务做校验。
- Portal 认证通过后，由 Gateway / Adapter 签发 launch/session 上下文。
- OPL 不保存 Portal 密码 hash，不读取 Portal 用户表，不和 Portal 共享数据库。

### 测试方法

- 在 OPL 原生登录框输入 Portal 邮箱密码，应进入同一用户上下文。
- 错误密码应明确失败。
- OPL 中不应出现 Portal 密码 hash 的持久化痕迹。
- `/api/auth/user` 应返回 Portal 侧映射出来的用户，而不是孤立的本地账号。

### 交付标准

- Portal 账号可以直接登录 OPL 原生登录框。
- 身份链路仍然低耦合。
- 没有密码同步、没有双用户库、没有共享身份表。

### 当前 v8 是否达到

- 未达到。

## 5. Portal 账号进入 OPL 后的任务空间、session trace、存储打通

### 目的

让 Portal 的账号、workspace、session 能够一直追到 OPL 的任务、trace、artifact 和存储目录。

### 商业化逻辑

商业化 SaaS 需要把“谁发起的、属于哪个 workspace、产生了什么 run、消耗了什么资源、文件放在哪里”连成一条链。没有这条链，后续就没有办法做账单、审计、权限和迁移。

### 实现方式

- Portal 维护 `tenant_id`、`portal_user_id`、`workspace_id`、`workspace_session_id`。
- OPL 维护 `runtime_session_id`、`run_id`、`trace_id`、`artifact_id`。
- Gateway / Adapter 负责把控制面上下文投影到运行面。
- 存储目录按 tenant/workspace/session/run 分层，不把所有数据塞进一个扁平目录。
- 动态 Job 必须写入资源标签，保证账单和日志能回到同一主体。

### 测试方法

- 从 Portal 进入 OPL 后创建 run，能从 run 反查 workspace、session 和 tenant。
- trace、artifact 和存储目录可以回到同一归属。
- 删除一个 workspace 时，不会影响其他 tenant 的数据。
- 运行面对象不会脱离 tenant 归属。

### 交付标准

- 任务空间、session trace、存储都能打通。
- 运行链路的归属关系完整且可追溯。
- 目录、标签和 API 的边界一致。

### 当前 v8 是否达到

- 未达到。

## 6. 本轮交付边界

- 只交付 v8 文档与本地验证计划，不推云。
- 不写入任何密钥或明文 Secret。
- 不把商业化逻辑做成临时补丁或兜底说明。
- 不把工程内部词直接暴露给普通用户页面。

## 7. 建议推进顺序

1. 先落文档，把目标、边界、测试和验收标准统一。
2. 再改 Portal 首页，把商业化入口和费用表达收紧。
3. 再改服务器商品化和 Job 调度，把价格选择变成真实资源开通。
4. 再做 OPL 原生登录框接入 Portal 账号密码。
5. 最后补齐任务空间、session trace、存储的全链路打通。

## 8. 验收口径

v8 不是“文档写完就算完成”，而是下面五件事都能被证明：

- 客户能透明选服务器和价格。
- 选择后，资源真的按所选规格进入集群。
- 首页足够商业化、足够简洁。
- Portal 账号能进入 OPL 原生登录框。
- OPL 的 run、trace、artifact 和 storage 能回到同一 tenant/workspace/session。
